## 1. 完善项清单（按执行批次）

### 批次一：通电与可观测（阻塞项）

- **H 接口健康检查**（kilo 估量：小）
  - `api.ts` 前置校验**密钥**非空（分类错误：密钥未配置 / 地址未配置 / 模型未选择）；
  - `updateDirector` 校验扩为**地址/密钥/模型三空**——R0 不止"密钥空"：地址错、模型名错、模型列表没拉都会静默失败；
  - 设置页接口区标红 + **新增「测试连接」按钮**（现只有"获取模型列表"；发一句短 chatCompletion 验证）；
  - 密钥空/接口不可用时**拦截自动推进**，杜绝静默 401 白烧。
  - **R1 实测结论（dsh 2026-10-07 00:30）**：用户端点 `127.0.0.1:8046/v1` 接受 60000 ✅；**不得**改小默认值（推理模型会空正文）。「测试连接」需新增一类诊断：**正文空 + completion_tokens 用满 = 推理吃满预算 → 提示调大 max_token**（不是接口错）。
- **I 引擎离线可观测**（kilo 估量：中）
  - 本幕页顶部状态条三态：`冷启动攒轮（第X/3轮）` / `引擎离线：上次失败原因+时间（连败N次，已自动暂停）` / `运行中：上次编排成功于 #X 楼`；
  - **状态条优先级高于冷启动提示**——否则又拿冷启动伪装故障（R0 的教训）；
  - 熔断计数持久化：**chat 变量 meta**（`连败次数/最后失败原因/最后失败时间/自动暂停`），失败时写、成功清零；不存账本快照（失败时不落盘）、不存全局（跨聊天串味）；
  - **连败 3 次自动暂停自动接管**（面板可手动恢复）——防 token 白烧。
- **F 剧终停引擎**：账本加 `已剧终` 标志，剧终结算后自动路径整体跳过（不调引擎不注入）；面板显示"已剧终"。
  - **补 kilo 发现的正确性缺陷**：剧终不可逆且**无二次确认**（死亡抉择即时落盘，误点"剧终结算"永久停引擎）→ 加二次确认 + 面板留"清除已剧终"出口。
- **K 指标账**（判据落地的前置，kilo 设计）
  - `伏笔.埋设章`（签发时由代码填当前 `章回.章号`）；
  - `指标.章节统计: {章号, 埋设数, 回收数, 张力峰, 张力谷, 起伏次数, 冲突推进数, 受挫数}[]`（章回转"已完结"时代码结算一条，有界 20 章）；
  - `指标.节拍历史 / 张力历史: {楼层, 值}[]`（每轮追加，有界 40）；
  - `指标.核验: {总, 未执行}`；
  - **`指标.本章累计: 章节统计`（2026-10-07 dsh 预读代码后补）**：`章节统计` 的 8 个字段**无法在结算那刻从有界历史重建**（历史仅 40 条，且不含"冲突阶段推进""伏笔状态变化"这类事件）→ 需一处**每轮就地累加**的落脚点；章更替时把整条 push 进 `章节统计`（有界 20）并重置。纯加法、可单测、与"有界裁切只在写入端"一致（累计只存一行，历史才裁）。
  - **章节结算触发面（同上补）**：**不能只看「进度 == 已完结」**——`账本数据.ts:35` 是**整体替换**章回，引擎若直接跳章（章号 1→2）而不标完结，旧章统计将永远结算不出（判据 1/3 失真）。触发条件取"章回发生更替"：**① 进度 非已完结 → 已完结；或 ② 章号变化**；且**幂等**（结算前查 `章节统计` 是否已有该章号）。
  - 成本：纯加法、零 AI 负担、用例可钉；收益：§3 五项判据全部可算，并直接喂面板"指标"卡。
- **J 指标可观测**（与 G 合并）：面板实时显示 §3 判据（回收率/波形/推进/受挫/执行率）——测试不用手工统计，用户也能自查。

## 3. "跌宕起伏"可度量判据（dsh 定义 + 需 K 落地）

| 指标 | 达标线（草案） | 依赖 |
| --- | --- | --- |
| 伏笔回收率 | 每章埋设伏笔，章末回收（引爆或明确消亡）≥ 2/3 | K：`伏笔.埋设章` + 章节统计 |
| 张力波形 | 曲线有波峰波谷（非单调/非水平），每章 ≥2 明显起伏（峰谷差 ≥3） | K：张力历史 |
| 冲突升级 | 每个活跃冲突 ≥2 次阶段推进（如 铺垫→升级→僵持），不许原地踏步 | K：冲突推进计数 |
| 真实挫折 | 档3下每 10 轮正文，主角 ≥1 次"实质性受挫"（损失当轮不可挽回） | K：节拍历史（受挫计数） |
| 指令执行率 | 主AI对导演指令执行率 ≥70%（核验统计；连续 2 次未执行=异常样本） | K：核验计数（+批次三证据引用提升可信度） |

> 达标线是**草案**，请用户与 kilo 确认（可调）；定义原则是"从账本可算、从面板可读、不靠主观印象"。

> **测试侧校准（kilo 意见，已采纳）**：
> - 「真实挫折」「指令执行率」是**代理指标**（前者=引擎有没有标"受挫"，后者=引擎自报的核验）——统计时**双轨报告**：账本自动统计 + 抽样正文人工/判定核验，达标线以人工判定为准。
> - **样本量**：10 轮 ≈ 1 章、埋 2~3 条伏笔，按章算回收率统计功效过低 → **小样本期聚合到全程**（全程回收率 ≥2/3 并附绝对数），跑完基线再决定是否按章判定。
> - **张力波形是半循环**（张力由代码按节拍折算、"喘息/阴影"也由代码强制）→ 结论表述限定为"系统整体有波形"，不直接归功于引擎文案质量。
> - **达标线先按草案跑一轮拿基线再调**——现在拍死容易过松/过严。

## 4. 测试方案（kilo 主导；用户已拍板四项 + kilo 的设计修正）

**用户已拍板（2026-10-07 00:22）**：
1. **密钥**：用户**已自行配好**（R0 根因解除，待实测确认）。
2. **测试载体**：**kilo 接管用户的 Chrome**（chrome-devtools `--autoConnect` → 127.0.0.1:8000）。
3. **规模**：**先跑 10 轮试水**（用户实测每层楼 5~6 分钟 → 10 轮 ≈ 1 小时）；跑完看基线再决定是否加码到 30 轮。
4. **环境**：用户当前只启用「剧情导演」+ 记忆插件（其余插件关掉）。**分两步走（2026-10-07 00:35 定）**：
   - **第 1 轮试水（10 轮）：关掉记忆插件**——试水首要任务是确认 R0 已修（引擎通电），少一个注入源便于归因；且省 token、提速（每层楼 5~6 分钟）。
   - **第 2 轮：开着记忆插件再跑**——共存验证（E6 读原始楼层+标签过滤 / E7 防混淆段）只有它开着才测得到，真实游玩环境亦如此。
   - 用**全新测试聊天/角色卡**，不在真实存档上跑。

**kilo 提出的设计修正（已采纳）**：
- **对照组改法（原设计跑不通）**：关插件侧**没有账本** → §3 五项里四项无从计算。改为：**单臂（开插件 10 轮）对阈值跑主判据** + **短基线（关插件 10 轮）仅用于正文盲评**（两段正文交判定者/判定模型问"哪段更跌宕"），不跑满 20×2。
- **固定条件**：同一角色卡 / 预设 / 模型（deepseek-flash）/ 温度 / 起手剧情；**测试期间不改任何设置**（改一次即作废重跑）；用**专用聊天或专用角色卡**，不污染真实存档。

- **单驱动者锁**：chrome-devtools 同一时间只留一个驱动者（谁连谁先发 `INFO` 通报）。
- **代码与实测错开**：测试途中 xiaoxi 改代码/热重载会影响当前聊天账本 → 改代码与实测必须**错开**（kilo 停测再改）。

- **开测前先出书面测试方案**（判据操作化定义、记录表、对照组处置）再由 kilo 动手。
- kilo 顺带验证：deepseek-flash 的 60000 max token 是否超限。
