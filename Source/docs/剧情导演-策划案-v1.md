## 0. 一句话定位

主AI不缺写作能力，缺的是**外置的剧情记忆与节奏指挥**。彼方管"人"，烟火管"世界"，**剧情导演管"戏"**——它不给主AI新设定、不记录世界事实，只负责剧情的编排：伏笔、冲突、节奏、挫折与反转，让任何世界观（修仙/科幻/现代都市）都能写出电视剧级的跌宕起伏。

## 1. 问题诊断：主AI为什么写不出长线剧情

三个**结构性**缺陷，各有各的病根，各对应一个机制：

| # | 缺陷 | 病根 | 对应机制 |
| --- | --- | --- | --- |
| 1 | **视野缺陷**：不埋伏笔、长线冲突断档、角色弧线原地踏步 | 主AI只能看到最近几层楼。第 5 楼埋的伏笔，第 40 楼早已出了视野——它不是不会埋，是**埋了也看不见** | §3.1 剧情账本（外置记忆） |
| 2 | **迎合缺陷**："舔玩家"——主角永远赢、队友永远不死，除非用户明令 | 写挫折/死亡需要**授权**。模型天性让用户满意，唯一敢用的授权来源是用户明令——但用户下令 = 用户被迫当编剧 = 剧透 + 出戏 | §3.3 导演指令（外部授权） |
| 3 | **结构缺陷**：平铺直叙，全程一个水位，没有"压制→爆发→喘息"的波形 | 没有节奏意识的对象。即使偶尔埋了伏笔，下一轮自己就忘了；没有任何东西告诉它"现在该收束了" | §3.2 导演引擎（结构规则） |

**关键洞察**：电视剧/电影好看，不是因为编剧比 AI 聪明，而是因为**结构存在于编剧的外部**——剧本大纲、节拍表、伏笔表、张力曲线图。演员（主AI）只负责演好这一幕。把同样的外部结构搬到酒馆里，主AI就能演出同样的剧情。

### 1.5 平台约束（设计前提，2026-10-06 19:30 用户确认）

1. **视野约束对双方成立**：不只主AI——**导演引擎的每次调用同样只读得到最近几层楼**（项目级限制，kilo 已知悉）。因此引擎按"无状态重启"设计：每次调用从账本快照恢复全部长线结构（章回/伏笔/冲突/弧线/上一道指令），最近正文只用于核验与素材——**账本就是导演的唯一长线记忆**。
2. **记忆插件共存**：用户可能装有记忆类插件——楼层正文（约 2000 字）被总结为几百字概要，每次生成向主AI注入**最相关的 20+ 条**。导演**不读取、不依赖、不排斥**记忆插件：账本与概要是互补的两套记忆（账本=**结构记忆**「戏演到哪了」，概要=**内容记忆**「发生过什么」），两者同时注入主AI不冲突；引擎读楼层沿用同族标签过滤机制，兼容各类记忆插件输出。
   - **记忆条目与读世界书（2026-10-06 19:50 用户确认）**：记忆插件生成的概要若以**世界书条目**形式存在，导演引擎读世界书时（同族机制：与主AI相同的激活逻辑）会**自然读到**——这不是依赖而是**宝贵补充**：引擎同样只读得到最近几层楼，记忆条目给了它视野之外的历史内容记忆。但引擎提示词必须加**防混淆段**（烟火 v2.1 对 `<记忆回溯>` 的既有处理）：记忆条目=剧情历史概要，**不是世界设定、不是行动指令、不得从中领取"必须推进的任务"**；执行核验只针对最近正文，概要中的旧事件不得当作"最近发生的"。
3. **零截断原则**：所有发送内容——引擎输入（正文/世界书/账本）、注入主AI的编剧备忘与本幕指令——**一律不截断："哪怕不发，也不要少发"**。截半句等于变味（例："把「伏笔」标题吃掉了——检查并修复" → "把「伏笔」标题吃"，语义完全改变）。内容规模控制靠**源头**：账本容量上限（§3.1）、读取范围设置（读几条正文/哪些世界书），而不是发送时静默砍半。同族先例：彼方 v4.14 起取消注入上限、烟火全量注入。
   - **裁定（dsh，2026-10-06）**：①**结构键字段上限属格式守卫，不算截断**——写入账本时短结构性字段（章主题/对手名/角色名等）按字段表上限守卫（烟火先例：`世界数据.ts` 明写"内容字段不截断，只保留结构性键的字段上限"）；**叙事性内容字段（伏笔内容/赌注/下一步/指令/弧线契机/章高潮事件）永不截断**。②**模型往返的错误反馈回喂残片属工程降噪，不算违规**（那是重试纠错引用，非剧情内容发送）——但正常发送通道一律零截断。③彼方现存两处发送前截断（主角人设 slice 4000 / 人设参考 slice 1500，`更新输入.ts`）属真违规——是否修复由用户拍板（既有插件行为变更）；**新插件绝不继承此行为**。

## 2. 同族生态与边界

| | 彼方 | 烟火 | 剧情导演（本插件） |
| --- | --- | --- | --- |
| 管什么 | 人：NPC 幕后生活 | 世界：势力/大事件自转 | **戏：剧情结构与节奏** |
| 注入给主AI的 | 事实（NPC 现状） | 事实（世界动向） | **编排（本幕该发生什么）** |
| 数据来源 | 最近正文 | 五层档案+正文 | 剧情账本+最近正文 |

- 与两前作**解耦**：任一未安装时本插件照常运转（沿用"彻底解耦"纪律）。
- 本插件**不生产设定**：世界设定来自世界书，人物生活来自彼方，世界大事来自烟火。它只做编排——"这场戏该怎么演"。
- **伏笔分界**（与烟火重叠的消解）：烟火的"伏笔"层是世界尺度暗线（服务于世界自转，主角未必卷入）；本插件的伏笔账是**剧情尺度**（服务于主角线的跌宕，必须最终汇聚到主线收束）。烟火伏笔引爆成事件后，若与主角线相关，导演可将其入账为剧情伏笔的"外部素材"。
  - **分界尺子**（与 kilo 收敛）：**线头的当事人是不是主角/当前场景/这一轮主AI演得到的人？** 是→导演；否（组织/远方/集体）→烟火。
  - 两边提示词各自声明尺度边界——这是提示词措辞问题，不是代码同步问题；实现上导演**不读烟火数据**、不重复维护世界层伏笔，保持同族「互不读取」纪律。轻微重叠（两条线头指向同一件事）可接受：一边是暗线事件源，一边是明线剧情钩子。

## 3. 核心机制：一本账 + 一个引擎 + 一道指令

### 3.1 剧情账本（治视野缺陷）

持久化在**楼层变量快照**（随楼层存亡、删楼回退、重roll回退——沿用彼方/烟火已验证的模式），由代码持有、AI 增量维护：

- **主线章回**：当前章号、章主题、本章计划的高潮事件、进度（铺垫/推进/收束/**已完结**——完结即归档可淘汰，滚动开新章）。这是"伏笔最后汇集到结局"的骨架——每章有既定汇合点。
- **伏笔账**：每条 `{编号, 内容(冻结), 埋设层, 状态, 预定回收窗口, 关联冲突}`。状态机：埋下→潜伏→发酵→已引爆→已消亡（终态=可淘汰）。**内容写下即冻结、只改状态**（仿彼方事务台账，防"玩偶变蛋糕"式泛化）；**回收窗口与关联冲突允许引擎改写**（策划授权，2026-10-06 验收期裁定：剧情未到收束点时延后窗口/改挂冲突是调度刚需，同"作废旧条另开新条"的彼方精神——冻结的是伏笔的"什么线头"，可挪的是"何时何地兑现"）；允许自然消亡（失义即删，不硬凑回收）。**编号全局单调递增、永不复用**（同烟火 event id 纪律）——指令层按编号引用，复用会让已下发指令指向错误对象。**预定回收窗口以章号锚定**（如"第 3 章收束前"），收束调度以此对齐。
- **冲突账**：每条 `{对手/对立面, 赌注(输了失去什么), 强度1-10, 阶段, 下一步}`。阶段：铺垫→升级→僵持→决战→收束→**已收档**（终态=可淘汰）。
- **角色弧线账**：每条 `{角色, 缺口(缺什么/错在哪), 当前阶段, 下一步契机}`。弧线是长线人物成长的锚，防止角色 50 楼后还是第 1 楼的性格复读。终态=**闭环**（缺口弥合/堕落完成），可淘汰。
- **当前指令**：**已下发的本幕指令本体**（节拍+引用编号+硬性要求+档位红线渲染）随账本一起存入快照——它是执行核验（rule 5）的比对对象，注入层刷新即丢，**快照是它唯一的持久位置**。
- **张力读数**：**代码折算为主，AI 校正为辅**——每幕节拍有固定张力增量表（由代码持有，节拍枚举冻结在字段表单一事实源），累计折算曲线；引擎 AI 报的 0-10 只作校正/兜底，防"随手填数字"让节奏规则乱触发。记录：当前张力值、距上次高潮的楼层数、连续低张力楼层数。
- **账本版本号**：绑定快照/指令/面板，防"新账本+旧指令"错配（注入一律从快照派生）。
- **容量上限与淘汰纪律**（防账本膨胀）：活跃章回 ≤1；伏笔 ≤8；冲突 ≤4；弧线 ≤5。淘汰顺序：终态（已引爆/已消亡/已收档/闭环）最旧优先；**满额且全进行中时允许临时突破上限 1 席，绝不静默丢弃新事件**（防死锁）；下一次有终态产生时回落。

### 3.2 导演引擎（治结构缺陷）

每 N 轮主AI回复后，**独立 API** 后台调用（同族模式，不占主生成通道）：
读「剧情账本 + 最近正文 + 世界书（同族激活逻辑）」→ 输出「账本更新 + 下一幕指令」。

与彼方/烟火的本质区别：它们是**记录器**（发生了什么→记下来），导演是**编剧**（发生了什么→接下来该怎么演）。因此引擎内置**代码层的结构规则**，不靠模型自觉（张力输入一律用代码折算值，见 §3.1）：

1. **张力曲线**：连续 N 轮高张力 → 强制安排喘息幕；连续 M 轮低张力 → 触发"山雨欲来"（静中埋险）。
2. **契诃夫之枪**：伏笔超过预定回收窗口 → 下一幕指令**优先安排回收**；但引擎判定已失去剧情意义的，**允许自然消亡**——**不得为兑现硬造**（烟火的教训写进同一规则，防"到期必须爆"的生产线倾向）。
3. **收束调度**：章进度逼近收束 → 伏笔账中未回收条目向本章高潮汇聚（窗口以章号锚定）。
4. **高潮后必有代价**：高潮幕之后强制至少一幕"余波"——**仅档 3/4 启用**（档 1/2 高潮本就罕见，强制余波会让低档变沉重）。
5. **执行核验**：引擎读最近正文核验快照里存着的上一道指令是否被执行（如"要求受挫，实际又赢了"）——未执行则记录，并升级下一道指令的强度/明确性。**升级有封顶**：最多连升 2 次、不得越当前强度档位与红线；用户"跳过本幕"即重置升级计数。核验是模型判断、会误判，封顶防螺旋升级到出戏。

### 3.3 导演指令（治迎合缺陷）——本插件的核心创新

注入给主AI的不是事实，是**编排**。每轮生成前就位（**指令有效期 = 至下一次引擎调用**；默认引擎每轮调用一次即 N=1，若用户调低频率则一道指令覆盖数轮），包含五块：

```
【本幕剧本】（外部导演已定，你必须执行，不得因玩家压力软化）
0. 当前设定：强度档位=第X档（附该档的一句话行为标准）；
   红线=[...]（如有，高于一切）
1. 本幕节拍：受挫 / 小胜 / 阴影 / 反转 / 兑现伏笔#N / 高潮 / 余波（节拍枚举冻结于字段表）
2. 硬性要求：按强度档位生成，如"本轮主角的计划必须遭遇实质性挫折，
   损失必须真实且不得在本轮内自行挽回"
3. 伏笔现场：当前在场/可触发的伏笔编号与一句话方向（不写台词）
4. 禁止事项：如"冲突#2 仍在升级期，本轮禁止解决它"
另：玩家本轮行动与本幕节拍冲突时的处理，按档缩放——
低档（1/2）：玩家行动正常生效，导演指令让位（玩家体验优先）；
高档（3/4）：玩家行动以戏剧方式失败或变形（玩家说"我道歉"≠冲突必须化解——道歉可以被误解）。
```

**反舔的原理**：挫折/死亡不是主AI自作主张（它不敢担责），而是**外部剧本的既定安排**——演员不为剧本里角色的死亡负责。出戏感的来源从来不是"主角输了"，而是"主角莫名地永远赢"。诚实的边界：插件只能**强指令+核验+升级（有封顶）**，无法物理强制主AI的笔——这是要在策划里向用户言明的极限。

## 4. 用户控制权（反舔 ≠ 失控）

- **戏剧强度滑杆**（4 档）：
  1. 轻松日常——小波折，无实质损失
  2. 平稳叙事——有起伏，主角基本赢
  3. 跌宕起伏（建议默认）——三幕波形，挫折-反转交替，配角可死、可失
  4. 残酷——主角可惨败，重要之物可永久失去，主线可失败
- **红线**：用户可钉死不可触碰项（"主角不死"、"XX 永远不背叛"）——红线优先于一切指令。
- **跳过本幕**：面板一键跳过当前指令（下一幕重新生成）——玩家当轮就想赢时的人道出口。
- **防剧透模式**（待用户拍板默认值）：面板默认折叠「未引爆伏笔」的具体内容与章回高潮计划——玩家看面板=剧透自己；关掉即上帝视角。
- 所有档位/红线/跳过都在悬浮球面板里，随聊天保存。

## 5. 数据与注入（已与 kilo 收敛定案）

- **存储**：状态本体存**楼层变量快照**（删楼/重roll/切分支自动回退，同族已验证机制）；聊天变量只存轻量索引；设置走全局变量。**注入内容一律从楼层快照派生（唯一真源）**。
- **注入通路：双层制**：
  - **事实层 → 世界书常驻条目「编剧备忘」**：当前章回、活跃冲突、伏笔登记表（带状态）、角色弧线——主AI每回合必读的长线事实，别的读世界书的环节也读得到（蓝灯常驻、防递归、切聊天重写，同族范式）。
  - **指令层 → `injectPrompts` + `GENERATION_AFTER_COMMANDS`（`in_chat`, depth 0）**：本幕导演指令——每回合变的即时命令，不进共享世界书（时点不对、污染角色卡），生成前**幂等重注**，顺带覆盖刷新/切聊天导致的注入丢失。仓库现成范式：`烟火/inject.ts`、`正文美化/注入.ts`。
  - **去重纪律**：事实层绝不写命令，指令层绝不复述事实、只按编号引用（如"兑现伏笔#3"）——两层各司其职，防主AI收到两份重复内容。**两层注入均零截断**（§1.5）。
- **触发时序**：MESSAGE_RECEIVED 后 800ms 防抖 → **异步**跑导演引擎（不阻塞用户输入）→ 写楼层快照 + 指令就绪；`GENERATION_AFTER_COMMANDS` 只幂等重注**已就绪**的指令，**绝不在生成事件里 await 慢 API**；用**账本版本号**绑定快照/指令/面板，防"新账本+旧指令"错配。常规节奏下用户敲下一条消息前早已完成；偶发未完成则沿用上一幕指令，不至于空。
- **可复用件**（kilo 盘点结论）：`共用/模型往返.ts`（165 行）、`共用/条目求值.ts`（549 行）**直接 import**；host 接缝/楼层快照/世界书注入/悬浮球壳/settings 五件为**同族复制件 fork**（快照机制是否抽 `共用/快照` 由实现侧定，抽不动就第三份 fork）；骨架粗估 ~1 个工作日，**大头是提示词与导演引擎设计（本策划案的核心交付）**。

## 5.5 删楼与回退语义（2026-10-06 20:20 用户问答沉淀）

账本长在楼层快照里——**删楼 = 剧情结构同步回退**，与幸存正文永远对齐（同族已验证机制）。分三种场景：

1. **删尾楼（回档重写，最常见）**：删多少楼，账本就回到多少楼之前的状态——伏笔状态/章回进度/张力读数全部回退到幸存快照，与幸存正文精确对齐，**不会相悖**。重roll 同理（新 swipe 无快照 → 自动回上一层状态）。
2. **删超过回退窗口**：快照保留份数有限（**默认 30，可调 1~100**；每轮推进 N=1 时快照每楼一份，30 份 ≈ 可回退 30 楼）。删几十楼把全部快照锚点删光 → 账本归零 → **重新冷启动**（攒 3~5 轮重建四本账）。不是相悖，是"重新开拍"；代价是重建期间不下指令。习惯大段删楼的用户可把保留份数调到 100（代价：聊天文件变大，每份快照约几 KB~十几 KB，同族烟火先例）。
3. **删中段楼**：账本跟**最新幸存快照**走（同族语义）——被删桥段里已引爆的伏笔、已推进的章回仍算"发生过"。这是中段删除的固有歧义（正文自己都"有后续无铺垫"）。逃生口：面板**账本修笔**（手动改伏笔/冲突/弧线状态，§6）或**清空重拍**（清空层机制，只从清空点之后重建，同族先例）。

**关于记忆插件概要**：实测环境中的记忆插件，**概要条目随楼层删除同步删除**（用户确认，2026-10-06 20:30）——删楼后世界书不会残留幽灵概要，主AI与导演冷启动重建都不会"记得"被删事件。§1.5 第 2 条的"防混淆段"仍然保留（它防的是语义混淆——概要=历史不是设定/指令——而不是防删楼残留）；README 无需"删楼后清理概要"指引。
